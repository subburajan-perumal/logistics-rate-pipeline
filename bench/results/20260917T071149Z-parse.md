# CSV parse profile — before/after (D-20)

Target: `BenchmarkParseCSV` (internal/parse), 20 000-row fathom-shaped CSV,
`go test -bench BenchmarkParseCSV -benchmem -count 3`, Go go1.27.0,
windows/amd64, 6C/12T laptop. Numbers are per parse of the whole file.

## Before

```
BenchmarkParseCSV-12    67   17631463 ns/op   57.85 MB/s   16066655 B/op   220018 allocs/op
BenchmarkParseCSV-12    68   18376928 ns/op   55.51 MB/s   16066496 B/op   220018 allocs/op
BenchmarkParseCSV-12    63   17708633 ns/op   57.60 MB/s   16066485 B/op   220018 allocs/op
```

`go tool pprof -top -sample_index=alloc_space` on the memory profile:

```
      flat  flat%   sum%        cum   cum%
    1.09GB 36.26% 36.26%     1.09GB 36.26%  parse.newRecord (inline)
    0.88GB 29.51% 65.77%     0.88GB 29.51%  strings.(*Builder).WriteString (inline)   ← record.ComputeHash
    0.49GB 16.40% 82.18%     0.49GB 16.40%  encoding/hex.EncodeToString (inline)      ← record.ComputeHash
    0.28GB  9.46% 91.63%     1.66GB 55.36%  record.(*RawRecord).ComputeHash
    0.16GB  5.43% 97.06%     0.16GB  5.43%  encoding/csv.(*Reader).readRecord
```

Diagnosis: 11 allocations per row, and 55 % of allocated bytes were in
`ComputeHash` — a `strings.Builder` growing through several sizes, its
final `String()` copy, and `hex.EncodeToString`'s intermediate slice. A
further allocation per row was the empty `Surcharges` slice literal.

## Change

- `record.ComputeHash`: assemble the canonical form in a `sync.Pool`-ed
  `[]byte` scratch buffer, hash with `sha256.Sum256`, hex-encode into a
  stack `[64]byte` and make exactly one string.
- `parse.newRecord`: share one zero-length `Surcharges` slice (encodes as
  `[]`; any append reallocates, so sharing is safe).

## After

```
BenchmarkParseCSV-12    	      81	  14986805 ns/op	  68.06 MB/s	 8233216 B/op	   80030 allocs/op
BenchmarkParseCSV-12    	      81	  14198565 ns/op	  71.84 MB/s	 8233314 B/op	   80030 allocs/op
BenchmarkParseCSV-12    	      90	  15428881 ns/op	  66.11 MB/s	 8233326 B/op	   80030 allocs/op
```

| metric | before | after | change |
|---|---|---|---|
| ns/op | 17 631 463 | 14986805 | ≈ −15 % |
| B/op | 16 066 655 | 8233314 | −49 % |
| allocs/op | 220 018 | 80030 | **−64 %** |

Remaining allocations per row (4): the `RawRecord` itself, the `float64`
for `Price`, the hash string, and `encoding/csv`'s field strings — all
inherent to emitting an owned record. Stopping here: the next step (record
pooling across the sink boundary) would complicate ownership for a stage
that is already ~5× faster than the network it sits behind.
